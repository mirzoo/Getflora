# Getflora Iterations

Этот файл фиксирует порядок развития проекта, чтобы не расползаться в сторону
лишних сервисов, преждевременного визуального полиша или сложной архитектуры.

## Как читать этот план

Изначально проект шел по плану из 10 итераций. После реализации базы часть
сценариев была сделана раньше и план был переразложен под фактическое состояние
кода. Текущий файл остается источником правды, а старый план соответствует ему
так:

- старая итерация 3 `Создание объявлений` -> текущие `Iteration 2` и
  отдельная добивка жизненного цикла объявления;
- старая итерация 4 `Авторизация` -> текущая `Iteration 3`;
- старая итерация 5 `Фото и хранилище` -> текущая `Iteration 7`;
- старая итерация 6 `Покупка и чат` -> текущие `Iteration 3` и `Iteration 5`;
- старая итерация 7 `Избранное` -> текущая `Iteration 3`;
- старая итерация 8 `Аукционы` -> текущая `Iteration 11`;
- старая итерация 9 `Админка` -> текущая `Iteration 10`;
- старая итерация 10 `Продакшен` -> текущая `Iteration 12`.

После закрытия фото добавлена промежуточная `Iteration 8: Staging Deploy`,
чтобы тестировать сайт по ссылке без локального запуска. Это не публичный
production launch.

Проект переименован в Getflora, публичный домен: `https://getflora.ru`.

Старая итерация 3 `Создание объявлений` закрыта в MVP-формате:

- форма создания объявления есть;
- несколько фото сохраняются как URL в `ListingImage`;
- объявление сохраняется в PostgreSQL;
- новое объявление публикуется как `ACTIVE`;
- базовая серверная валидация есть;
- срок жизни активного объявления: 48 часов.

Настоящая загрузка файлов не входит в эту добивку: она остается отдельной
итерацией `Real Photo Upload`, чтобы не смешивать создание объявления с S3.

## Принципы

- Сначала рабочий пользовательский сценарий, потом полировка.
- Проект остается монолитом на Next.js: frontend, backend, auth, admin,
  database и storage живут в одном репозитории.
- Внешние сервисы подключаются через небольшие адаптеры и env-переменные.
- Нельзя завязывать production на один недоступный или нестабильный в России
  сервис.
- Vercel можно использовать только как удобный demo-вариант, но не как
  обязательную production-платформу.
- Production должен уметь жить на Docker/VPS с обычным PostgreSQL и
  S3-compatible storage.

## Iteration 5: Manual Scenario QA

Status: done, checklist in `docs/QA_ITERATION_5.md`.

Цель: проверить проект как marketplace, а не как набор экранов.

Подробный чеклист: `docs/QA_ITERATION_5.md`.

Сценарий:

1. Пользователь A публикует объявление.
2. Пользователь B добавляет объявление в избранное.
3. Пользователь B покупает и пишет продавцу.
4. Пользователь A видит чат с покупателем.
5. Пользователь A отмечает объявление как проданное.

Критерий готовности:

- Сценарий проходит без ручного вмешательства в базу.
- Ошибки и пустые состояния понятны.
- Продавец и покупатель не путаются в ролях.

## Iteration 7: Real Photo Upload

Status: done for MVP, QA in `docs/QA_ITERATION_7.md`.

Цель: заменить URL-фото на настоящую загрузку файлов.

Production-подход:

- S3-compatible storage.
- Адаптер в `services`.
- Env-переменные для endpoint, bucket, ключей и public URL.
- Локальная разработка может использовать MinIO.

Сервисы, которые стоит рассматривать с учетом России:

- Selectel Object Storage.
- Yandex Object Storage.
- Собственный MinIO на VPS.
- Другой S3-compatible provider, если он доступен пользователям и команде.

7A:

- локальный MinIO добавлен в Docker Compose;
- форма создания объявления принимает файлы JPG/PNG/WebP;
- backend загружает фото в S3-compatible bucket;
- в базе по-прежнему сохраняются URL в `ListingImage`;
- ссылки на фото оставлены как запасной вариант.

7B:

- редактирование фото через загрузку файлов добавлено;
- старые MinIO-файлы удаляются из storage, если их убрали из списка;
- UI управления фото показывает кнопку добавления, превью и удаление по hover.

QA:

- storage lifecycle пройден автоматически;
- UI создания и редактирования проверен через браузер;
- ручная проверка с реальными пользовательскими фото остается полезной перед
  деплоем.

Не делать:

- Не завязываться на AWS-only API.
- Не хранить файлы в репозитории.
- Не смешивать upload-логику с UI-компонентами.

## Iteration 8: Staging Deploy

Status: done for staging MVP, details in `docs/STAGING_DEPLOY.md`.

Цель: опубликовать внутреннюю staging-версию, чтобы тестировать сайт по ссылке
без локального запуска.

Важно: это не полноценный production launch и не публичный запуск.

Зачем:

- не поднимать Docker/PostgreSQL/MinIO локально каждый раз;
- проверять гипотезу и UX на настоящей ссылке;
- выкатывать новые изменения в одну staging-среду;
- не блокироваться на production-auth до внутреннего тестирования.

Состав:

- Timeweb Cloud VPS поднят;
- PostgreSQL и MinIO подняты через Docker Compose;
- bucket для фото создан и открыт на чтение;
- проект склонирован на VPS;
- миграции применены через `prisma migrate deploy`;
- приложение временно запускается через Node.js + PM2;
- Nginx reverse proxy подключен на порт `80`;
- основной A/B marketplace-flow вручную проверен на staging;
- Dockerfile для app отложен: Docker build зависал на `npm install`;
- staging-инструкция зафиксирована в `docs/STAGING_DEPLOY.md`.

Known issues:

- preview выбранных фото в форме пока не отображается стабильно;
- мобильные модалки требуют отдельной UI-проработки;
- фото с камеры iPhone требуют client-side compression/resize перед upload;
- мобильный доступ по голому `http://IP` нестабилен;
- позже подключить домен и HTTPS;
- описать backup/reset staging-данных.

Ограничения:

- пользователей пока не звать массово;
- данные staging можно сбрасывать;
- текущая временная auth допустима только для внутреннего теста;
- перед публичным запуском нужна `Production Auth`.

## Iteration 9: Production Auth

Status: in progress — magic-link-first onboarding реализован в коде, нужна проверка на `https://getflora.ru`.

Цель: заменить временную auth на production-вариант.

Выбранный MVP-подход:

- **magic-link-first onboarding** как основной вход;
- email + пароль как fallback для существующих аккаунтов и ручной регистрации;
- email magic link через Resend после настройки DNS/domain verification;
- server-side `Session`;
- httpOnly session cookie;
- старые staging-пользователи без пароля могут привязать пароль при регистрации с тем же email.

Magic link:

- одноразовый token hash хранится server-side;
- TTL ссылки — 15 минут;
- базовый rate limit — 3 запроса на email за 10 минут;
- после клика создается обычная server-side session;
- если аккаунта нет, пользователь попадает на `/auth/complete` и задает имя.

Текущий статус на домене:

- Resend domain `getflora.ru` verified, DNS подтверждён;
- PR #10 с magic link смёржен и задеплоен на VPS;
- migration `20260606000100_add_magic_link_tokens` применена;
- письмо `Вход в Getflora` доходит через Resend;
- callback bug закрыт: `/auth/magic` — route handler, cookie через `NextResponse`;
- magic-link-first flow: email -> письмо -> вход или `/auth/complete`.

Осталось проверить на домене:

- новый пользователь: email -> письмо -> имя -> session;
- существующий пользователь: email -> письмо -> session;
- fallback: регистрация/вход по паролю;
- выход и refresh session;
- старый staging-пользователь без пароля: magic link или привязка пароля.

Отложено до финальной проверки email provider:

- подтверждение email письмом отдельно от magic link.

Ограничения для России:

- Не делать обязательный вход через Google/Apple/GitHub.
- Email-провайдер должен быть доступен и стабилен.
- Auth должна работать на Docker/VPS.
