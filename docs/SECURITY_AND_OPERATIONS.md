# Security And Operations Rules

Этот документ дополняет `AGENTS.md`. Используй его для задач, которые затрагивают
auth, пользовательские данные, файлы, чат, объявления, БД, аналитику, логи,
админку, инфраструктуру или публичные формы.

## Общий Принцип
- Любое изменение должно быть минимальным, проверяемым и обратимым.
- Перед добавлением новой логики проверь существующие сервисы, хелперы, repository и локальные паттерны.
- Не добавляй новые зависимости без сильной причины и явного объяснения.
- Оптимизируй реальные узкие места или очевидный техдолг, а не гипотетическое будущее.

## Backend И Бизнес-Логика
- Не размещай бизнес-логику прямо в UI-компонентах.
- Server actions/routes должны быть тонкими: валидация входа, вызов сервиса, возврат результата.
- Бизнес-правила держи в `features/*/services`.
- Работу с БД держи в repository/service слое, не размазывай Prisma-запросы по проекту.
- Все проверки владельца, прав доступа и статусов выполняй на сервере.
- Никогда не доверяй данным с клиента: `userId`, `listingId`, `status`, `price`, `imageUrl`, `role`.

## Авторизация И Доступ
- Любое действие пользователя должно проверять текущую серверную сессию.
- Нельзя использовать cookie/userId как единственное доказательство личности в production-логике.
- Для изменения объявления проверяй:
  - пользователь авторизован;
  - пользователь владелец объявления;
  - объявление в допустимом статусе;
  - действие не нарушает lifecycle.
- Не меняй auth, cookies, session или permissions без отдельного объяснения риска.

## Валидация Данных
- Валидируй все входные данные на сервере.
- Проверяй строки на длину, пустые значения и недопустимые форматы.
- Для чисел проверяй диапазоны: цена, количество цветов, лимиты.
- Для файлов проверяй размер, MIME type, расширение и количество.
- Не сохраняй в БД сырые данные, если они могут привести к XSS, мусору или поломке UI.

## Файлы И Изображения
- Не доверяй имени файла от пользователя.
- Генерируй безопасные server-side имена для файлов.
- Не разрешай загрузку произвольных типов файлов.
- Не логируй приватные S3 URL, ключи, access tokens и secret values.
- При удалении фото проверяй, что файл принадлежит объявлению и объявление принадлежит пользователю.

## Антиспам И Злоупотребления
- Для публичных действий учитывай rate limit или место, куда его можно безопасно добавить.
- Особенно защищай:
  - вход/регистрацию;
  - создание объявлений;
  - отправку сообщений;
  - загрузку фото;
  - жалобы;
  - поиск.
- Не добавляй массовые операции без ограничений, пагинации или фильтров.

## Производительность
- Не делай N+1 запросы к БД.
- Для списков используй пагинацию или явные лимиты.
- Не загружай лишние поля из БД, если они не нужны UI.
- Не запускай тяжелые cleanup/cron-задачи внутри обычного page render, если есть возможность вынести их в отдельную команду или background job.
- Перед кешированием объясни:
  - что кешируется;
  - на сколько;
  - как инвалидируется;
  - что будет при устаревших данных.

## Аналитика И События
- Для важных пользовательских действий предусматривай аналитическое событие.
- Не отправляй в аналитику персональные данные, cookies, токены, полные сообщения чата или приватные URL.
- Полезные события для ReBloom:
  - `listing_created`
  - `listing_viewed`
  - `listing_favorited`
  - `seller_contacted`
  - `message_sent`
  - `listing_marked_sold`
  - `listing_expired`
  - `photo_upload_failed`
  - `report_created`
- Метаданные события должны быть минимальными: id сущностей, тип действия, timestamp и безопасные технические параметры.

## Логи И Ошибки
- Логируй ошибки так, чтобы их можно было расследовать.
- Не логируй:
  - пароли;
  - токены;
  - cookies;
  - приватные ключи;
  - содержимое личных сообщений;
  - персональные данные без необходимости.
- Для ошибок используй понятные коды и контекст: action, listingId, userId, requestId если есть.
- Ошибки пользователя и ошибки сервера разделяй.

## База Данных И Миграции
- Не меняй схему БД без объяснения последствий.
- Для новых полей продумывай nullable/default/backfill.
- Не удаляй поля или таблицы без явного согласия.
- После изменения Prisma schema обязательно предложи команды миграции и проверки.
- Не делай destructive migration без предупреждения.

## Админские Инструменты
- Если появляется новый пользовательский риск, подумай, нужен ли админский инструмент:
  - посмотреть жалобы;
  - заблокировать объявление;
  - заблокировать пользователя;
  - посмотреть проблемные загрузки;
  - вручную исправить статус.
- Админские действия должны иметь серверную проверку прав.

## Проверка Перед Завершением
- Проверь, не сломаны ли существующие сценарии.
- Проверь, есть ли серверная валидация и проверка прав доступа.
- Проверь, нет ли утечки секретов или персональных данных.
- Проверь, не появились ли лишние зависимости.
- Проверь, не ухудшилась ли производительность списков и главной страницы.
- Укажи, как протестировать изменение.
